# Mobile status dashboard

Open the Cloudflare Worker origin at `/mobile` from an iPhone or Android browser. The static page is public but contains no operational data. To load the dashboard, enter the existing `ENGINE_API_TOKEN`; it is held only in page memory and is not written to local/session storage, cookies, URLs, or logs. Disconnect or close the page to clear it.

The page calls the authenticated, read-only `GET /v1/mobile/status` endpoint. It reports task-state counts, append-only paper-event counts, latest paper event, latest captured market snapshot, D1 provider request/token totals, recorded model inference costs, Worker Cron/watchdog status, and validated Engine CI / default Task Runner inference-gate snapshots from the Staging D1 audit ledger. CI and policy snapshots are marked stale after 24 hours; missing or invalid snapshots remain unknown. The page no longer calls the public GitHub API directly. Model costs are recorded costs only; unreported or external spend is not inferred. It does not expose mutation controls. The endpoint checks the D1 schema migration ledger and omits paper/provider metrics cleanly when their additive migrations have not yet been applied. It also reports whether migration `0005_telegram_webhook_receipts` is present. This is a schema-readiness signal only: it does not inspect or reveal Telegram secrets, prove that the webhook is configured, or register the webhook with Telegram. The scheduled Task Runner emits only the corresponding sanitized `available`, `not_available`, or `unknown` flag in its issue status comment; it does not expose the receipt table contents or webhook credentials.

The merged Worker code adds a dashboard panel for the latest Cloudflare Worker Cron heartbeat from the existing D1 audit ledger, including the schedule and stale-lease recovery counts. The authenticated status response also includes `task_runner_watchdog`: a boolean readiness flag, names of missing GitHub App settings, the last sanitized dispatch-request metadata, and the last durable dispatch-intent timestamp. The page displays these fields without exposing any secret values. A ready configuration is not proof of a successful GitHub API dispatch; verify a real `workflow_dispatch` Task Runner run and its bounded batch result before declaring the fallback operational. The Task Runner issue status now also includes the sanitized timestamp, schedule and recovery counts. The heartbeat confirms only that the Worker Cron handler ran; it does not confirm that the separate GitHub Actions Python Task Runner ran or processed tasks.

The mobile dashboard now reads an explicit latest research scan and per-source freshness observations from the D1 audit ledger. These are written by the scheduled GitHub/Crossref discovery workflow through the authenticated scan telemetry endpoint, and are never inferred from Cron heartbeats, CI success, or market snapshots. The scan/source contract, bounded reason codes, 24-hour freshness threshold, and idempotent event identity are documented in [research-scan-telemetry.md](research-scan-telemetry.md). Missing or malformed records remain unknown; old observations are marked stale.

The following are intentionally shown as unavailable rather than guessed: scan-run heartbeat and market-source freshness. The default Task Runner inference gate is mirrored from the committed policy and the effective repository variable; it is explicitly scoped to the scheduled Task Runner and does not describe one-off Staging smoke workflows. The latest captured market snapshot is shown separately and is not presented as a scan completion or source-freshness guarantee. These require explicit, separately verified ingestion contracts before they can be displayed as current facts.

Security headers include no-store, no-referrer, nosniff, and a restrictive Content Security Policy. CI health is ingested by a main-only GitHub Actions job into the dedicated Staging D1 audit ledger. The publisher verifies the Staging and production database IDs differ, writes only two sanitized metadata events, and reads them back. It does not write to production D1 or expose provider credentials. The page stores no access token persistently.

The CI telemetry publisher is currently Staging-only. The production Worker and production D1 are unchanged; promoting the new dashboard fields to production remains a separately gated deployment decision. The telemetry job does not apply migrations, change secrets, enable inference, or enable external actions.
