# نظام البحث والتطوير المستمر — Raawaa Autonomous Engine

**الحالة:** وثيقة تشغيلية مدمجة في `main`؛ توحّد عمل البحث والتطوير حول البنية الحالية، ولا تفعّل بذاتها استدلال النماذج أو الأدوات الخارجية أو النشر.
**الهدف:** تحويل البحث الموجود إلى وظيفة R&D قابلة للقياس، قابلة للاستئناف، ومتدرجة في الصلاحيات، مع إعادة استخدام البنية الحالية.

## 1. القرار التنفيذي

لا تنشئ محرك بحث ثانياً ولا منسقاً أو مجدولاً أو مخزن ذاكرة موازياً. استخدم المكونات القائمة:

- `engine/research_discovery.py` للاكتشاف العام المحدود.
- `.github/workflows/research-discovery.yml` للجدولة اليومية واللقطة.
- `scripts/triage_research_candidates.py` للفرز الحتمي.
- D1 `research_candidates` للذاكرة البحثية الدائمة عند تفعيل إعداد الاستمرارية.
- D1 audit telemetry لقياس نجاح الفحص وحداثة المصادر.
- Task Store / Remote Task Store لإدارة المهام عندما يكون نوع المهمة وعقده مدعومين.
- سجل الوكلاء الحالي بوصفه توصيفاً للأدوار، لا دليلاً على وجود وكلاء نموذجية عاملة.
- Tool Broker بعد اكتمال مراجعته ودمجه، مع بقاء الأدوات غير المسجلة ممنوعة.

يجب أن يظل الفرق واضحاً بين:
1. **R&D Discovery:** جمع بيانات عامة وفرزها آلياً.
2. **R&D Analysis:** مقارنة الأدلة بالقدرات الحالية وإنتاج فرص.
3. **R&D Engineering:** تحويل فرصة معتمدة إلى تغيير واختباره.
4. **R&D Runtime:** تشغيل وكيل مستقل فعلياً؛ هذا غير مفعل ما دامت مسارات الاستدلال والأدوات غير مفعلة.

## 2. خط الأساس الفعلي الذي يجب الحفاظ عليه

بحسب فحص المستودع في 2026-11-03:

تخزين المرشحين في D1 يدعم الآن GitHub وCrossref وarXiv وSearXNG. الترحيل `0011_research_source_expansion` يعيد بناء الجدول لتوسيع قيد `source` مع الحفاظ على سجل المراجعة بالكامل، ويُطبّع Worker معرّفات arXiv وروابط SearXNG (HTTPS فقط، ورفض العناوين الرقمية والمضيفات المحلية) دون جلب أي محتوى. لا تُجلب الملخصات ولا النصوص الكاملة، ويظل التحقق من الترخيص منفصلًا، ولا يصبح التوسع فعّالًا في Staging قبل تطبيق الترحيل هناك.
- الاكتشاف الحالي لا يثبّت أو ينسخ أو يشغّل أي مستودع مرشح.
- لقطة الاكتشاف وتقرير الفرز وتقرير فجوات القدرات تحتفظ بها GitHub Actions artifacts لمدة 30 يوماً.
- حفظ المرشحين في D1 مشروط بمتغير `RAAWAA_ENGINE_RESEARCH_PERSISTENCE=enabled`; أما telemetry فمسار مستقل.
- الفرز لا يثبت الترخيص أو الأمان أو الجودة؛ كل المرشحين غير معتمدين حتى المراجعة. الدرجة الحالية تعتمد أساساً على metadata مثل حداثة الدفع والنجوم واللغة ووسوم الصلة، ولا تقيس أداء الأداة أو ملاءمتها الفعلية أو أمنها؛ لذلك هي ترتيب لمراجعة بشرية وليست ترتيباً موثوقاً لقيمة التبني.
- `config/agents.json` سجل توصيفي؛ لا يشغّل نماذج أو أدوات خارجية.
- Task Runner يعمل كدفعات محدودة، ولا يثبت وجود خدمة Python دائمة أو تشغيل 24/7. نجاح دفعة فارغة لا يثبت إتمام مهمة فعلية.
- مسارات الاستدلال الحي ما زالت معطلة افتراضياً، وسياسة المزود ذات hard-stop غير مثبتة.
- دُمج PR #414 لإضافة Tool Broker deny-by-default؛ لا توجد adapters خارجية مسجلة في مسار التشغيل الحالي، ولا ينبغي وصف البوابة بأنها متصلة بالوكلاء حتى يتم اختبار هذا الربط.
- `scripts/analyze_capability_gaps.py` يقارن موضوعات البحث بخط أساس المستودع ويصدر task proposals من نوع `capability_proposal` تتضمن الأثر/المخاطر/التكلفة/التعقيد، معايير القبول وخطة التراجع. هي بيانات مراجعة داخل artifact فقط: لا كتابة في Task Store، ولا تنفيذ أو اعتماد تلقائي. التحليل offline ولا يقرأ قيم GitHub Variables أو سجلات D1 أو الحالة الحية.

أي اختلاف لاحق يجب حسمه بإعادة فحص SHA والملفات ونتائج CI، لا بالاعتماد على هذه اللقطة.

## 3. مهمة قسم R&D

يعمل القسم على ستة مسارات مترابطة:

1. **Architecture & Reliability:** كشف الانحراف المعماري، نقاط الفشل، التكرار، مشاكل الاستعادة، وجدوى التوسع.
2. **Agent & Workflow Research:** تقييم أطر الوكلاء، المنسقين، coding agents، التقييم، واستمرارية التنفيذ دون تكرار ما يقدمه المحرك.
3. **Model & Provider Intelligence:** مقارنة النماذج والمزودين والسياقات والسرعة والجودة والتكلفة والترخيص والخصوصية؛ لا inference دون بوابات الموافقة الحالية.
4. **Tools, MCP & Skills:** اكتشاف الأدوات والمهارات، والتحقق من إمكانية الوصول الفعلية، ثم مراجعة الأمان قبل أي اعتماد.
5. **Memory & Knowledge:** جودة الذاكرة والاسترجاع، المصدر والثقة والحداثة، منع التكرار والتعارض والادعاءات المختلقة.
6. **Testing, Security & Cost:** تغطية الاختبارات، حقن التعليمات، سلسلة التوريد، العزل، الاعتمادية، استهلاك الحصص والتكلفة.

## 4. الأدوار والمسؤوليات

هذه أدوار عمل وليست ادعاءً بوجود عمليات نموذجية مستقلة. يمكن أن ينفذها مدير واحد أو عدة وكلاء فقط عندما يكون runtime متاحاً ومثبتاً.

| الدور | المسؤولية | التسليم |
|---|---|---|
| R&D Director | ترتيب المحفظة، منع التكرار، تثبيت حدود النطاق | خطة دورة وقرارات |
| Research Lead | المصادر، التحقق، المقارنة، التراخيص | Evidence brief |
| Capability Architect | مقارنة الاكتشافات مع البنية والقدرات الحالية | Gap analysis |
| Experiment Engineer | تجارب صغيرة قابلة للإعادة | Benchmark / prototype |
| Security & Privacy Reviewer | مراجعة مستقلة للمخاطر والصلاحيات والبيانات | Security decision |
| Cost & Reliability Analyst | قياس الكلفة والفشل والتشغيل والاستعادة | Cost/reliability report |
| Release Reviewer | مراجعة diff والاختبارات والتراجع | PR review / release gate |
| Knowledge Curator | إزالة التكرار وربط النتائج بالمصادر | Decision / finding record |

لا يراجع الوكيل عمله وحده في التغييرات المؤثرة. إذا لم يتوفر مراجع مستقل، تبقى النتيجة `IMPLEMENTED_NOT_VERIFIED` أو `BLOCKED` ولا توصف بأنها معتمدة.

## 5. دورة R&D التشغيلية

### يومياً — دورة قصيرة منخفضة التكلفة

1. قراءة السياسات وإعادة بناء الحالة من المستودع وSHA الحالي.
2. فحص PRs وIssues وCI والجدولة والمهام غير المنجزة.
3. تشغيل مصادر الاكتشاف المسموحة ضمن حدودها؛ إعادة استخدام workflow القائم.
4. التحقق من صلاحية المصدر وحداثة المعلومة وتكرارها.
5. تشغيل الفرز الحتمي ثم `scripts/analyze_capability_gaps.py` لمقارنة موضوعات الاكتشاف بخط أساس المستودع.
6. إخراج تقرير فرص `PROPOSED` كـ artifact؛ لا ينشئ مهاماً تلقائياً ولا يثبت الحالة الحية للخدمات.
7. حفظ checkpoint وروابط الأدلة والمهام التالية.

### أسبوعياً — مراجعة هندسية

- مراجعة فجوات المعمارية، تغطية الاختبارات، فشل workflows، التبعيات والثغرات.
- مقارنة مرشح واحد أو اثنين فقط مع الوضع الحالي والبدائل.
- تشغيل benchmark محلي/مجاني على بيانات عامة أو اصطناعية فقط.
- إعداد PR صغير واحد عند وجود فائدة مثبتة وبوابة أمان مكتملة.
- تسجيل البدائل المرفوضة وأسباب رفضها لمنع إعادة البحث بلا دليل جديد.

### شهرياً — مراجعة استراتيجية

- مراجعة تغيرات النماذج والأسعار والحصص والتراخيص وشروط البيانات.
- تقييم تكلفة الصيانة والتعقيد التراكمي لكل مكون.
- حذف/تعطيل أي تكامل غير مستخدم فقط عبر إجراء مراجعة وتراجع معتمد، لا تلقائياً.
- إعادة ترتيب خريطة القدرات والـ roadmap استناداً إلى نتائج القياس.

**الجدولة الحالية:** workflow الاكتشاف اليومي موجود. هذا لا يثبت تشغيل دورة تحليل هندسي نموذجية كل يوم. لا تدّعِ تفعيل دورية إضافية قبل وجود workflow ونتيجة تشغيل موثقة.

## 6. ترتيب الفرص

قيّم كل عامل من 0 إلى 5، حيث الأعلى أفضل للأثر والثقة والملاءمة وقابلية التراجع، والأعلى أسوأ للمخاطر والتكلفة والتعقيد وعبء الصيانة.

استخدم درجة تفسيرية لا قراراً آلياً نهائياً:

`priority = 20 × (0.30I + 0.25C + 0.20R + 0.10V + 0.15S) − 4 × (0.35K + 0.25X + 0.20T + 0.20B)`

حيث:
- `I`: أثر قابل للقياس.
- `C`: ثقة الأدلة.
- `R`: صلة مباشرة بمشكلة مثبتة في المحرك.
- `V`: قابلية التراجع.
- `S`: قابلية الصيانة (كلما زادت كان العبء أقل).
- `K`: المخاطر.
- `X`: التكلفة المتكررة.
- `T`: تعقيد التنفيذ.
- `B`: عبء الصيانة (كلما زاد كان أسوأ).

تُقاس جميع القيم من 0 إلى 5، وتُحصر النتيجة النهائية بين 0 و100. لا تستخدم الدرجة لتجاوز بوابات المنع أو الموافقات.

ثم طبّق بوابات رفض مستقلة:
- أي مخاطر أمنية حرجة غير معالجة = `BLOCKED`.
- ترخيص/شروط/سعر/حصة غير معروف = غير مؤهل للتبني.
- لا baseline أو لا معيار قبول = `PROPOSED` فقط.
- لا تفوق مادي على الموجود أو بديل أبسط = رفض أو تأجيل.
- أي تكلفة جديدة أو صلاحية جديدة أو نشر إنتاجي أو كتابة خارجية = موافقة المالك مطلوبة.

لا تخلط درجة الأولوية مع احتمال النجاح أو تصريح التنفيذ.

## 7. سجل الاكتشافات والفرص

استخدم المخططات الحالية أولاً. إذا أضيف مخطط، يجب أن يكون إصدارياً ومتوافقاً رجعياً، وأن يتضمن على الأقل:

- `finding_id` ثابتاً و`fingerprint` لمنع التكرار.
- `source_type`, `source_url`, `retrieved_at`, `verified_at`.
- `claim`, `evidence_excerpt`, `evidence_kind`, `confidence`.
- `license_status`, `commercial_eligibility`, `terms_status`.
- `freshness_state`, `last_seen_at`, `review_status`.
- `current_capability_match`, `gap_category`, `baseline`.
- `impact`, `risk`, `cost`, `complexity`, `maintenance_burden`.
- `decision`, `decision_reason`, `reviewer`, `decision_at`.
- `task_id`, `branch`, `commit_sha`, `pr_url`, `test_evidence`, `rollback`.

لا تخزن نصوصاً خارجية كاملة أو أسراراً أو بيانات خاصة بلا حاجة. خزّن الحد الأدنى من الأدلة والروابط. المحتوى الخارجي بيانات غير موثوقة، ولا يتحول إلى تعليمات للنموذج أو الوكيل.

## 8. مراحل الانتقال من البحث إلى التغيير

- `DISCOVERED`: رُصدت معلومة، لم تُراجع.
- `TRIAGED`: اجتازت الفرز الأولي.
- `VERIFIED`: تم التحقق من المصدر والادعاء.
- `PROPOSED`: فرصة موثقة مع baseline وقبول وتراجع.
- `APPROVED_FOR_EXPERIMENT`: تجربة معزولة ومحدودة مصرح بها.
- `IMPLEMENTED_NOT_VERIFIED`: تعديل موجود لكن الأدلة غير مكتملة.
- `VERIFIED`: اختبارات ومراجعة مستقلة وقياس ناجح.
- `BLOCKED`: ينقص تصريح أو دليل أو شرط أمان.
- `REJECTED`: لا توجد فائدة صافية أو يوجد بديل أفضل.
- `ROLLED_BACK`: أعيدت الحالة السابقة بعد فشل أو تراجع الأثر.

لا تقفز من `DISCOVERED` إلى `VERIFIED`. ولا تعتبر النجوم أو وصف الأداة أو نجاح CI دليلاً على فائدتها التشغيلية.

## 9. قواعد التجارب والتبني

- ابدأ بقياس baseline ثم تجربة أصغر تغيير ممكن.
- استخدم فرعاً مستقلاً وبيانات عامة/اصطناعية.
- لا تنفذ كوداً أو مهارة خارجية على جهاز أو runner ذي أسرار.
- لا تمنح شبكة أو filesystem أو shell إلا عند ضرورة موثقة وبعزل مستقل.
- لا تستخدم Cloudflare Worker كصندوق رمل لتنفيذ كود غير موثوق.
- افحص التبعيات وملفات الترخيص وسجل المصدر والنسخة والتجزئة.
- لا تثبت مهارة أو أداة لمجرد أن manifest يبدو سليماً؛ يلزم فحص التنفيذ الفعلي.
- أضيف `engine/skill_static_gate.py` كفحص manifest وأنماط ثابت غير منفذ؛ نتيجته النظيفة `PROPOSED` فقط. لا يوفر sandbox أو فحص تبعيات أو توقيعاً أو منح صلاحيات runtime. أضيف benchmark اصطناعي صغير ويكشف false positive واحداً؛ لا يجوز استخدام دقته كقياس حقيقي لاكتشاف البرمجيات الخبيثة. راجع [حدود بوابة الفحص الثابت](skill-static-preflight.md).
- يجب أن يكون التراجع محدداً ومختبراً أو موصوفاً بما يكفي لإثبات إمكانيته.
- لا دمج إلى main إذا كانت سياسة المراجعة أو CI أو حماية الفرع غير مستوفاة.
- لا نشر إنتاجي أو تغيير secrets أو صلاحيات أو فوترة دون موافقة منفصلة.

## 10. ميزانية R&D

- الإنفاق الجديد المستهدف: `$0`.
- سقف المشروع يبقى كما هو في `docs/operations.md`: لا رفع ولا إعادة تخصيص.
- لا تستخدم API مدفوعاً أو خطة مدفوعة أو اشتراكاً أو رصيداً قد يسبب فوترة.
- لا تعتبر Free tier مجانياً تجارياً أو بلا حدود قبل التحقق من الحساب والشروط والحصة.
- راقب أرصدة أدوات البحث ذات الحصص مثل Firecrawl قبل استخدامها؛ إذا لم يمكن التحقق من الرصيد، لا تنفذ crawl كثيفاً.
- استخدم GitHub Actions وCloudflare ضمن حدود الخطة المجانية فقط، وتوقف عند حدود الاستخدام.
- لا ترسل بيانات سرية أو خاصة إلى نموذج أو خدمة بحث خارجية.
- سجل تكلفة فعلية أو `UNKNOWN`؛ لا تسجل صفراً إلا إذا ثبت عدم وجود طلب/استهلاك مدفوع.

## 11. مؤشرات الأداء

اعرض المؤشرات التالية لكل أسبوع/شهر:

- مصادر جرى فحصها / مصادر فشلت / نسبة حداثة المصادر.
- نتائج جديدة بعد إزالة التكرار.
- نسبة الادعاءات التي تحققت من مصدر أولي.
- فرص مقترحة / مقبولة / مرفوضة / مؤجلة.
- نسبة الفرص التي تحولت إلى تجارب ثم إلى تحسينات مثبتة.
- متوسط زمن اكتشاف الفجوة إلى قرارها.
- تغييرات سببت regressions أو احتاجت rollback.
- أثر الاختبارات والأداء والموثوقية قبل/بعد.
- استهلاك API والـ Actions والـ storage والإنفاق الفعلي.
- عدد الادعاءات غير المدعومة؛ الهدف صفر.

لا تحسّن عدد الاكتشافات على حساب جودة الأدلة أو تقليل المخاطر.

## 12. ما يمكن تشغيله الآن وما لا يمكن

### يمكن تشغيله ضمن الوضع الحالي

- اكتشاف GitHub/Crossref/arXiv اليومي المحدود؛ SearXNG اختياري وغير مفعّل حتى توفير endpoint.
- الفرز الحتمي دون استدلال نماذج.
- تقارير بحث ومراجعة هندسية يدوية/مساعدة بأدوات ChatGPT المتاحة.
- تحليل فجوات حتمي offline وتقرير capability-gap artifact عبر workflow البحث اليومي.
- إنشاء مهام ومقترحات وفروع وPRs ضمن صلاحيات GitHub المتاحة.
- الاختبارات المحلية وCI ومراجعة النتائج.
- تحديث سجل القرارات والتوثيق.

### غير مفعل أو غير مثبت

- وكيل R&D مستقل يستدعي نموذجاً تلقائياً.
- استيعاب كل الويب والأبحاث وHugging Face وCVE وMCP/Plugins بشكل موحد.
- تحليل فجوات مدعوم بنموذج أو تحقق من الحالة الحية، وتحويل تلقائي للفرص إلى مهام: غير منفذ. الموجود حالياً تحليل حتمي لملفات المستودع فقط.
- استيراد/تشغيل مهارات خارجية في sandbox معتمد.
- وصول المحرك إلى أدوات ChatGPT المتصلة أو مهاراته تلقائياً.
- تشغيل دائم 24/7 أو تنفيذ تلقائي غير مراقب.
- نشر MCP Connector في حساب ChatGPT الحالي دون التحقق من أهلية المنتج والحساب.

لا ترفع هذه العناصر إلى `VERIFIED` إلا بعد تنفيذ واختبار وتحقق مستقل.

## 13. Definition of Done

تعتبر دورة R&D مكتملة فقط عندما تحتوي على:

1. حالة المستودع وSHA والـ PRs والـ CI.
2. مصادر أصلية وتواريخ تحقق وأدلة.
3. baseline ومقارنة ببديل أو بالموجود.
4. تقييم مخاطر وتكلفة وترخيص وخصوصية.
5. قرار واضح وأسبابه.
6. إن نُفذ تغيير: branch/commit/PR واختبارات على SHA المطابق.
7. مراجعة مستقلة وخطة تراجع.
8. أثر مقاس أو تصريح صريح بأن الأثر لم يُقَس.
9. checkpoint للاستئناف من دون تكرار.
10. أعلى فرصة آمنة للدورة التالية.

**قاعدة الاستمرار:** بعد كل دورة، ابدأ التالية ما دام هناك وقت وميزانية وصلاحية. عند نهاية الجلسة احفظ checkpoint واضحاً؛ لا تدّعِ أن العمل يستمر بعد انتهاء الجلسة إلا إذا أثبتته جدولة أو خدمة منشورة تعمل فعلاً.

## 15. خريطة الكود والوكلاء والمهام

لا تدمج ثلاثة أنواع مختلفة من العلاقات في قاعدة واحدة:

1. **خريطة الكود والتبعيات:** Graphify OSS هو المرشح لتوليدها محلياً من AST وملفات الإعدادات؛ التجربة تستخدم `--code-only` دون نموذج أو خدمة مستضافة.
2. **خريطة الأدوار والقدرات:** `config/project-agent-map.json` سجل معماري ثابت يربط أدوار `config/agents.json` بالمكونات والأدوات والفجوات. كل علاقة تميز بين `declared_only` و`implemented` و`not_connected`، ولا تدعي أن الدور الوصفي وكيل عامل.
3. **خريطة العمل الحية:** تبقى مهام D1/Task Store واعتمادياتها وlanes والـleases مصدر الحقيقة. لا تنسخها إلى Graphify أو قاعدة Graph ثانية.

**قرار التجربة:** تشغيل Graphify OSS المثبت الإصدار في job مستقل ضمن Workflow الاكتشاف نفسه، بصلاحية قراءة فقط، دون أسرار أو inference، وحفظ artifact لمدة 7 أيام. لا يوقف فشل هذا الـjob اكتشاف الأبحاث، ولا يعتمد أي runtime على artifact.

**قرار المنصات:** لا نعتمد GraphClaw أو Noriq كمنسق بديل الآن؛ كلاهما يعيد جزءاً من طبقة المهام والـclaims التي يملكها المحرك. نستفيد من أنماطهما فقط إذا أثبت قياس gap محدد. لا نضيف قاعدة بيانات أو scheduler أو orchestrator موازياً.

**المطلوب قبل اعتماد Graphify:** نجاح CI على فرع التجربة، وجود graph غير فارغ، صحة المخطط ومسارات الأدلة، عدم وجود مسارات محلية مطلقة، ثم اختبار مجموعة أسئلة معمارية ثابتة ومقارنة الإجابات بالبحث الخام. يبقى الرجوع إلى البحث الحالي متاحاً، ولا يتوقف أي مسار عمل على Graphify.

## 16. سجل اعتماد البدائل والاحتياط

السجل الموحد للحالة الفعلية والبدائل والاحتياط هو [Capability adoption and fallback register](adoption-matrix-2026-11-07.md). لا يكفي وجود بديل في provider profile أو مستودع GitHub لتسميته احتياطياً عاملاً؛ يجب إثبات الأهلية والتشغيل والتحويل إليه والعودة منه باختبار Staging موثق.

حتى 2026-11-07 لا يوجد مسار نموذج مؤهل ومفعل، وGPT-OSS 120B ليس احتياطاً صالحاً بسبب رفض الصلاحية HTTP 403 وعدم تحقق المجانية. Graphify تجربة لخريطة الكود، وD1 Task Store يبقى مصدر الحقيقة للمهام الحية. لا نعتمد منسقاً أو قاعدة بيانات ثانية قبل إثبات فجوة لا تسدها البنية الحالية.
