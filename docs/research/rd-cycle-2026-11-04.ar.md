## 1. الخلاصة التنفيذية

النتيجة الأهم ليست العثور على إطار وكلاء آخر؛ بل إن البنية الحالية تحتوي بالفعل على معظم عناصر التحكم والتشغيل، بينما ما ينقصها هو **ربط هذه العناصر في مسار تنفيذي فعلي آمن ومقاس**.

القرارات البحثية:

1. **لا تضف منسقاً أو طابوراً أو قاعدة بيانات أو نظام ذاكرة موازياً.** أبقِ D1 مصدر الحقيقة للمهام والحصص والإنفاق، واستخدم Python core وWorker الحاليين.
2. **لا تعتبر سجل الوكلاء فريقاً عاملاً.** config/agents.json توصيف أدوار، وengine/agent_runtime.py يعيد عقد dry-run ولا يستدعي نموذجاً.
3. **الفجوة التنفيذية الرئيسية هي مدير عمليات/وكلاء فعلي**: لا يوجد process manager يشغّل CLI خارجياً ويشرف عليه ويوقف جميع الأبناء عند انتهاء المهلة أو فقدان lease. batch_runner.py يحد قبول مهام جديدة، لكنه لا يفرض مهلة قتل قاطعة على المهمة الجارية.
4. **لا يوجد مراجع مستقل داخل المحرك حتى الآن.** CI وPRs وبروتوكول المجلس ليست بديلاً عن وحدة مراجعة مستقلة تمنع العامل من اعتماد عمله.
5. **Tool Broker آمن افتراضياً لكنه غير موصول بوكلاء فعليين.** لا توجد adapters مسجلة أو audit sink دائم في مسار runtime؛ مصفوفة الصلاحيات الحالية تسمح فقط بقراءة ملفات/قائمة المستودع.
6. **أفضل مرشح جديد يستحق متابعة حسابية هو Cloudflare Workers AI GLM-4.7-Flash**: نموذج مستضاف، MIT على أوزانه، tool calling و131K context وZero Data Retention بحسب صفحة Cloudflare، مع حصة مجانية مشتركة 10,000 Neurons/day. لكنه ليس «مجاني بلا حدود»، وحساب Cloudflare وخطة الاستخدام لم يثبتا، وPR #405 ليس مسار inference ولا يفرض سقفاً على استهلاك الحساب كله.
7. **Groq Free GPT-OSS يبقى أقوى مسار معروف التحقق حسابياً** في المشروع، لكنه معطل، وبيانات التحقق في ملفات profiles مؤرخة 1 نوفمبر ويجب تحديثها قبل أي تفعيل. Qwen مسجل Preview وليس مرشح إنتاج.
8. **Nemotron 3.5 Lightning يبقى مرشحاً معطلاً**: واجهة NVIDIA التجريبية مجانية حالياً لكن لا يوجد حد رقمي ثابت موثق للحساب ولا hard stop مثبت ولا حسم كافٍ لشروط API والاحتفاظ.
9. **لا حاجة الآن إلى OpenHands أو LangGraph أو Agno أو Mem0 أو Qdrant كاعتمادات إنتاجية.** يمكن الاستفادة من أنماط ACP/MCP وCloudflare Agents SDK، لكن إدخال منصة كاملة سيكرر وظائف قائمة قبل إثبات الحاجة.
10. **حسّن مصادر البحث قبل تحسين عدد المرشحين:** أضف مستقبلاً بيانات MCP Registry وOSV وOpenSSF Scorecard وHugging Face كاكتشاف metadata محدود، ولا تنفذ أو تثبت أي مرشح تلقائياً.

## 2. خط الأساس الحي للمحرك

### ما هو موجود فعلياً

- Python core، سياسات fail-closed، Task Store وD1 remote task ledger، idempotency، leases وheartbeat وfencing.
- SQLite محلي للذاكرة، وD1 لحالة المهام والحصص والدفاتر المالية؛ ذاكرة SQLite المحلية ليست ذاكرة مشتركة مضمونة عبر GitHub runners المؤقتة.
- Workflow planner حتمي يتحقق من DAG والتبعيات، وdependency-aware queue claims/release موجودة ومختبرة على SQLite وD1؛ لكن التخطيط لا يعني أن dispatcher النموذج متعدد الخطوات أصبح فعالاً.
- D1 quota ledger وmonetary reservations/settlement وper-task attribution وkill-switch وzero-cost-only live gateway.
- Task Runner دفعات محدودة، وجدولة GitHub وWorker watchdog/Cron؛ هذا ليس Python process دائم 24/7.
- Research Discovery يومي محدود: GitHub وCrossref وarXiv، وSearXNG اختياري غير مفعل حتى توفير endpoint موثوق.
- Capability-gap analysis حتمي/offline ويخرج مقترحات فقط، ولا ينشئ مهاماً أو يوافق أو ينفذ تلقائياً.
- Tool Broker deny-by-default، سجل مهارات read-only، وفحص static أولي للمهارات؛ لا واحد منها يثبت صلاحية تشغيل كود خارجي.

### تحديث مهم: Cloudflare Agents SDK

وثائق Cloudflare المحدثة 29 أكتوبر 2026 تصف الوكيل كـDurable Object ذي lifecycle؛ ليس process يعمل بلا توقف. الحالة الدائمة والجداول والجدولة وfiber checkpoints تبقى بعد hibernation/restart، بينما المتغيرات المؤقتة والـtimers والـclosures لا تبقى. وتوصي Cloudflare بـWorkflows للـpipelines المستقلة الثقيلة وبـfibers للمهام طويلة الأجل داخل agent.

هذا تطور يستحق متابعة، لكنه لا يلغي السؤال المعماري: **هل نحتاج DO أصلاً؟** لدينا D1 ledger وWorker Cron وGitHub Task Runner وWorkflow spike. إضافة DO قبل إثبات gap ستكرر state/scheduler وتزيد migrations والتكلفة المحتملة. Free plan لديه حدود فعلية للطلبات والـduration وSQLite reads/writes/storage؛ تجاوز حدود Workers Free يوقف العمليات، بينما Workers Paid قد يفرض رسوماً.

### ACP وMCP

- ACP معيار JSON-RPC over stdio بين coding agent والعميل. OpenHands يستخدمه لتشغيل Codex/Gemini CLI/Pi/OpenCode/Claude Code كعمليات فرعية. هذا معيار ربط agents، وليس sandbox ولا policy engine ولا quota ledger.
- ACP subprocess قد يستخدم login أو API credentials خاصة به ويتجاوز بوابة النموذج والحصص الخاصة بالمحرك؛ لا تربطه قبل process manager وعزل حقيقي وcredential isolation.
- MCP معيار مفيد لربط الأدوات، لكنه لا يمنح الأداة ثقة أو صلاحية تلقائية. يجب أن تمر كل استدعاءات MCP عبر Tool Broker، مع role/task/tool/environment allowlist، schema validation، audit، idempotency وموافقة منفصلة للكتابة.
- لا تنقل 1,912 أداة ChatGPT إلى المحرك. هذه تعريفات tools في بيئة ChatGPT الحالية، وليست 1,912 خدمة مستقلة أو credentials قابلة للنقل.

### حساب تقريبي لحصة Cloudflare GLM-4.7-Flash

وفق تسعير Cloudflare المنشور: 5,500 Neurons لكل مليون input tokens و36,400 لكل مليون output tokens. طلب افتراضي 2,000 input + 512 output يستهلك نحو 29.64 Neurons؛ أي قرابة 337 طلباً من هذا الحجم ضمن 10,000 Neurons/day **قبل احتساب أي استهلاك آخر في الحساب**. هذا حساب نظري من السعر المنشور وليس benchmark أو حصة مضمونة. طلب أطول أو مخرجات أكثر يخفض عدد الطلبات.

## 5. منظومة الأدوات والمهارات الحالية

### لقطة بيئة ChatGPT في هذه الجلسة

- **1,912 تعريف أداة قابلة للاستدعاء ضمن 62 namespace group.**
- **259 skill definitions** متاحة عبر skill catalog.
- تشمل المجموعات: GitHub، Firecrawl، Exa، Parallel Search، Consensus، SciSpace، Hugging Face، Context7، Notion، Slack، Figma، Supabase، Activepieces، Adobe، Render، Runzumi، وغيرها.
- هذه الأرقام هي لقطة جلسة ChatGPT وليست 1,912 اتصالاً مستقلاً أو 259 وكيلاً. تعريف الأداة لا يثبت consent/connection/account entitlement، والـskill ملف تعليمات وليس runtime credential أو executable capability.

### حدود النقل إلى المحرك

المحرك لا يستطيع استدعاء أدوات ChatGPT أو skills المتاحة في هذه الجلسة تلقائياً. يجب أن يمتلك adapter خاصاً به، وcredential مستقل محدود، وسياسة تفويض واختبارات. الحالة الحالية:
- GitHub هو تكامل المستودع الفعلي، مع GitHub App داخل مسارات التحكم الموثقة.
- Activepieces كان بلا connections/flows في آخر inventory؛ لا تعتمد عليه كمشغل.
- Firecrawl رصيد مدفوع/محدود وليس خدمة مجانية دائمة؛ لا تستخدم crawl واسعاً دون مراجعة الرصيد.
- Runzumi لم يكن workspace consent متاحاً؛ GitHub Actions APIs/logs هي مصدر CI.
- TinyFish مستبعد من operating path؛ APIs أولاً.
- Figma/Adobe/Notion/Slack/Supabase/SEO/marketing connectors أدوات مساعدة في ChatGPT ولا تنتقل إلى runtime المحرك دون adapters منفصلة.
- Tool Broker الحالي لا يحتوي إلا grants قراءة repository files/listing؛ لا يوجد public web search أو shell أو test execution أو MCP server مسجل في runtime.

**القرار:** لا bulk-install ولا bulk-connect. ابدأ بأدوات قليلة ذات قيمة تشغيلية واضحة: GitHub read-only، مصادر بحث عامة محددة، ثم اختبار أمني مستقل. كل write action يبقى خارج الصلاحيات الافتراضية.

## 6. تطوير طبقة البحث والاكتشاف

الاكتشاف الحالي جيد كبداية لكنه يقيس popularity/metadata أكثر مما يقيس الثقة الأمنية أو ملاءمة التشغيل. المرشحون الجدد التاليون يستحقون دراسة إدخالهم كمصادر metadata فقط:

| المصدر | ما يضيفه | الاستخدام المقترح | الحدود |
|---|---|---|---|
| Official MCP Registry | قائمة MCP servers وإصداراتها وmetadata، API read-only للبحث والتحديثات | اكتشاف MCP tools حسب اسم/نسخة/transport وتسجيل المصدر | Registry في preview ولا يضمن uptime/durability؛ وجود listing لا يعني الأمان |
| OSV.dev API | استعلام vulnerabilities حسب package/version/commit | فحص إصدارات dependencies أو commit المرشح قبل توصية التبني | لا يثبت خلو المشروع من كل الثغرات؛ يتطلب معرفة package versions |
| OpenSSF Scorecard API | checks عن ممارسات أمن المستودعات | إضافة security signals مستقلة إلى تقييم GitHub candidates | score ليس اعتماداً أمنياً؛ افحص كل finding وسياقه |
| Hugging Face Hub API | model/dataset metadata، tags، license field، last modified وdownloads | توسيع اكتشاف النماذج والأوزان وdatasets | license metadata لا تغني عن قراءة الترخيص الفعلي وشروط inference host |

### شكل الفرز المقترح

لا تجعل عدد stars أو downloads معيار الثقة. اجعل النتيجة عدة محاور منفصلة:
- **Capability fit:** المهمة المطلوبة، context، tool calling، modalities، language.
- **Operational fit:** host، CPU/RAM/GPU، cold start، persistence، process supervision.
- **Security:** OSV advisories، Scorecard، source pinning، SBOM، permissions، network policy.
- **Legal/privacy:** model license، hosted API terms، retention، training use، commercial use.
- **Cost/quotas:** verified account tier، exact quota، reset window، hard stop، paid fallback.
- **Maintenance:** releases، maintainers، dependency churn، deprecation risk.

أي missing evidence يجب أن يبقى UNKNOWN لا أن يتحول إلى درجة منخفضة المخاطر. ولا يتم clone/install/run للمرشحين ضمن discovery workflow الحالي.

## 7. الذاكرة والمعرفة

- لا تضف vector database الآن. لا يوجد baseline يثبت أن SQLite retrieval أو structured project facts فشلت.
- المشكلة الأوضح هي دوام الذاكرة ومصدرها: SQLite المحلي في runner مؤقت، بينما D1 هو مصدر الحقيقة للمهام والحصص. يجب أن تكون قرارات المشروع والنتائج البحثية طويلة الأمد قابلة للاسترجاع من مخزن دائم موثوق قبل أي embeddings.
- أولوية البحث: provenance لكل fact (source URL/file/commit/line/time), confidence، freshness، conflict state، owner decision، expiry/retention، dedup fingerprint.
- افصل memory types: project facts، decisions، research findings، task outcomes، operational snapshots. لا تخلط نتائج web untrusted مع تعليمات التشغيل أو سياسة المشروع.
- لا تستخدم Mem0/Letta/Zep/Graphiti إلا بعد benchmark يقارن precision/recall والـlatency والتكلفة والخصوصية مقابل البحث المنظم الحالي.

## 8. الأمان والاعتمادية

### Sandbox / Codespaces

Issue #440 ما زال release blocker. PR #517 الحالي لا يمثل إثبات عزل. المراجعة المستقلة المسجلة في #464 أظهرت مشكلات محددة في fingerprint المفتاح، قبول image/probe، اختبار host path بدلاً من mount path، تفسير OSError كإثبات PID limit، توافق cgroup v1/v2، symlink إلى host root، وtimeout cleanup. CI unit tests على PR #517 نجحت، لكن Staging jobs skipped؛ هذا لا يثبت sandbox containment.

**القرار:** لا live adversarial dispatch ولا Codespaces executor activation حتى تصحيح المراجعة، وإثبات كل acceptance tests على exact head، ومراجعة مستقلة ثانية. لا تعتبر أي اختبار فشل في probe إثبات escape، ولا أي اختبار ناجح عادي إثبات عزل.

### Tool Broker / Skills

- يجب أن يكون broker هو بوابة كل أداة، لا مجرد check اختياري داخل agent.
- durable audit sink قبل وبعد كل side effect، مع حظر replay عند ambiguity.
- كل adapter يحدد timeout/response size/network egress/schema/idempotency.
- مهارات الطرف الثالث تعامل كبيانات غير موثوقة؛ static scanner لا يثبت السلامة ولا يعوض sandbox.
- فصل reviewer عن executor في credentials والـtools والـwrite permissions.

### Supply chain / deployment

Issue #521 يسجل خطر استخدام Wrangler moving major tag في مرحلة secret upload/deploy، وإعادة كتابة bearer secret مع كل نشر. هذا ليس دليلاً على اختراق، لكنه reproducibility/recovery risk يجب أن يراجع قبل أي نشر إنتاجي. لا نشر أو تعديل أسرار ضمن هذه الدورة.

## 10. أين تناقصت العوائد البحثية؟

بعد مراجعة Microsoft Agent Framework وPydanticAI وLangGraph وAgno وOpenHands وGoose وCloudflare Workflows وAgents SDK وOpenAI Agents SDK/API، تتكرر النتيجة نفسها: **إضافة framework كامل لا تعالج الفجوات الأساسية، بل تنشئ scheduler/state/policy surface إضافياً.**

وصل البحث العام عن «أفضل framework» إلى عوائد متناقصة. لن أواصل تعداد frameworks أو أدوات مشابهة دون ظهور فجوة قياس جديدة.

الاستمرار عالي القيمة الآن ليس البحث عن framework سابع؛ بل الحصول على baseline واختبار محدود عند السماح به:
1. task completion success rate،
2. policy violation / denied action rate،
3. lease loss and recovery،
4. hard timeout and descendant cleanup،
5. independent reviewer disagreement rate،
6. tokens/neurons per accepted task،
7. latency and retry rate،
8. persistence across runner restart،
9. tool-call audit completeness،
10. cost remains exactly $0.

لا يمكن قياس جودة نموذج فعلياً دون inference، لذلك لا أختلق benchmark من جداول vendor.

## 11. نقاط نقاش لاحقة مع Arena

1. هل يبقى D1 canonical ledger، مع استخدام Cloudflare Agents SDK كـwake-up/lifecycle فقط إن لزم، أم أن ذلك يكرر Worker Cron بلا فائدة؟

3. كيف نفصل independent reviewer عن executor في model identity والcredentials والtool permissions؟
4. هل GLM-4.7-Flash عبر Cloudflare Workers AI أفضل من direct Z.ai API؟ يجب الفصل بين ترخيص الأوزان وشروط Cloudflare host وشروط Z.ai direct API.

6. ما أبسط شكل لذاكرة D1 provenance يمنع ضياع المعرفة وتعارضها دون vector DB؟
7. ما هو acceptance benchmark الذي يثبت تحسناً مادياً قبل إضافة أي framework أو tool adapter؟
