# تقييم بحثي: NVIDIA SkillSpector لبوابة أمان المهارات

**تاريخ التقييم:** 2026-11-03  
**الحالة:** `PROPOSED` — مرشح يستحق تجربة معزولة، غير مثبت في المحرك وغير معتمد للاستيراد.  
**النطاق:** تقييم أولي مبني على سجل الاكتشاف الحالي والوثائق الرسمية للمشروع؛ ليس تدقيقاً أمنياً كاملاً للكود أو التبعيات.

## 1. لماذا ظهر المرشح؟

في آخر تشغيل موثق لـ `Scheduled Open-Source Research Discovery` على main SHA `074a5cbc358ccc6e12ddc8c5bfd8c030b6c4ff7e`، نجح workflow رقم [41688634324](https://github.com/ghith93/raawaa-autonomous-engine/actions/runs/41688634324). تقرير الفرز احتوى 41 مرشح GitHub و10 سجلات Crossref، وجاء `NVIDIA/SkillSpector` ضمن أعلى مرشحي GitHub بدرجة metadata مقدارها 100 وأولوية high.

هذا لا يعني أنه آمن أو الأفضل؛ جميع المرشحين في التقرير ظلوا `unreviewed`، ولم تُجرَ أي استدعاءات نماذج (`model_calls=0`). كما أن درجة الفرز الحالية مبنية على إشارات metadata مثل النشاط والنجوم واللغة والترخيص المعلن، وليست قياساً أمنياً أو benchmark لقدرة الأداة.

## 2. ما الذي يقدمه؟

بحسب مستودع NVIDIA ووثائقه:
- ماسح ثابت لمهارات الوكلاء ومحتوياتها قبل التثبيت.
- يذكر المستودع 71 نمط ثغرة ضمن 17 فئة، منها prompt injection، تسريب البيانات، تصعيد الصلاحيات، مخاطر سلسلة التوريد، تسميم الذاكرة، إساءة استخدام الأدوات، ومخاطر MCP.
- تحليل ثابت يتضمن قواعد وأنماطاً وتحليل AST، مع تقييم دلالي اختياري عبر LLM.
- مخرجات JSON وMarkdown وSARIF، ما قد يسمح بدمجه لاحقاً في CI دون الحاجة إلى MCP.
- استعلامات OSV.dev للتحقق من ثغرات تبعيات معروفة، مع fallback محلي عند تعذر المصدر.
- مستودع GitHub يعلن Apache-2.0؛ يجب مراجعة ملف LICENSE الفعلي وملفات التبعيات قبل أي اعتماد.

المصادر:
- https://github.com/NVIDIA/SkillSpector
- https://docs.nvidia.com/skills/scanning-agent-skills
- https://docs.nvidia.com/skills/agent-skill-trust-pipeline

## 3. حدود الثقة والمخاطر

**SkillSpector ليس صندوقاً رملياً.** يذكر المشروع أنه لا يشغّل المهارة المفحوصة؛ لكنه لا يعزلها إذا قرر المشغل تثبيتها لاحقاً. لذلك لا يستبدل sandbox أو runtime policy.

مخاطر يجب ضبطها:
1. وضع LLM الاختياري يرسل محتوى ملفات المهارة إلى مزود النموذج. يمنع استخدامه في Raawaa ما لم تُراجع سياسة البيانات والمزود وتُعتمد صراحة. أي تجربة أولى يجب أن تستخدم `--no-llm`.
2. فحص التبعيات يتصل بـ OSV.dev ويرسل إحداثيات أسماء الحزم وإصداراتها. إذا كان المطلوب منع الشبكة، يجب استخدام fallback offline والتحقق من سلوك الإصدار المثبت.
3. خدمة MCP عبر HTTP غير مصممة لتكون مكشوفة للعامة؛ توثيق المشروع يقول إن النقل بلا مصادقة ويقيده إلى loopback. لا ننشرها ولا نربطها بخادم بعيد.
4. الماسح نفسه كود خارجي يحتاج مراجعة مصدر وتبعيات وحدود موارد؛ لا نشغله في runner يحتوي أسرار GitHub أو Cloudflare.
5. الفحص الثابت قد ينتج false positives وfalse negatives، وقد لا يفهم كل اللغات أو الملفات الثنائية/المشفرة أو السلوك وقت التشغيل.
6. فحص أمني ناجح لا يثبت أن المهارة مفيدة أو أنها تحسن أداء الوكيل.

وتؤكد وثائق NVIDIA أن خط الثقة الكامل يفصل بين ثلاثة أمور: الفحص الأمني، إزالة التكرار، وتقييم المهارة على مهام فعلية؛ كما يفصل التوقيع عن هذه المراحل. النجاح في الفحص وحده لا يكفي للنشر.

## 4. مقارنة مع حاجة المحرك

| حاجة Raawaa | SkillSpector | الحكم |
|---|---|---|
| كشف تعليمات خبيثة/حقن | مدعوم جزئياً بفحوص ثابتة | مفيد كطبقة أولى |
| كشف سلوكيات كود خطرة | تحليل AST وأنماط | مفيد، يحتاج اختبار |
| تحليل التبعيات | OSV.dev | مفيد مع ضبط egress |
| عزل التنفيذ | غير موجود | يجب أن نوفره مستقلاً |
| منع صلاحيات زائدة | يكتشف أنماطاً ومؤشرات | لا يفرض صلاحيات runtime |
| قياس فائدة المهارة | ليس دور الماسح | يحتاج benchmark منفصل |
| توقيع/إثبات هوية الإصدار | ليس بديلاً عن توقيع الإصدار | تحقق منفصل مطلوب |
| تكلفة صفر مؤكدة | لا يمكن استنتاجها من المستودع | يلزم تشغيل static-only ضمن بيئة مجانية معروفة |

## 5. القرار المقترح

لا تستورد SkillSpector إلى runtime ولا تسجله كـ MCP ولا تثبّت أي مهارة بناءً على نتيجته وحدها.

**التجربة الآمنة التالية المقترحة:**
1. تثبيت commit محدد من SkillSpector بعد مراجعة المصدر وLICENSE وSBOM/lockfile.
2. تشغيله في GitHub Actions ephemeral job منفصل، بصلاحية `contents:read` فقط، دون أسرار أو tokens أو اتصال بمخازن الإنتاج.
3. استخدام مجموعة fixtures اصطناعية benign/malicious تغطي prompt injection، exfiltration، privilege escalation، shell execution، dependency typosquatting، وMCP tool poisoning.
4. تشغيل `--no-llm`، ومنع egress العام؛ إما تعطيل OSV network واستخدام fallback المحلي أو السماح فقط بطلب OSV محدود بعد موافقة أمنية.
5. وضع حدود وقت/ذاكرة/حجم ملفات/حجم أرشيف/عدد ملفات، وإيقاف التشغيل عند نقص التغطية.
6. قياس precision/recall على corpus معروف، وزمن الفحص، وحجم التبعيات، والنتائج غير الحاسمة.
7. مراجعة مستقلة ثم قرار: اعتماد كأداة فحص ثابت فقط، أو رفضه، أو البحث عن بديل أخف.

لا تنفذ هذه التجربة حتى يتم إثبات أن runner معزول عن الأسرار وأن صلاحياته لا تسمح بأي كتابة خارجية.
